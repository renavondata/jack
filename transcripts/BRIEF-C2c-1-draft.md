## 0. The law of this window is a file, and what binds the file

`transcripts/windows/C2c-1.json` is this window: its opening rule and preconditions, its promotion forecast, its end, its budget rule, its numbers and the constants SPEC fixes, its processes, what is frozen, its criteria with the evidence each reads, its reads, and what is reserved to the sovereign. `tools/status.py` reads the window it assesses from `transcripts/windows/<subject>.json`; every earlier window gets a file too (a precondition), so that history is assessed the same way. This prose is commentary: where it and the file differ, the file governs and the difference is a finding.

**Binding.** The trusted-base digest does not cover `transcripts/` (SPEC §10.1) and `transcripts/windows/` is in counsel's own scope, so the file is bound outside counsel's reach, in this order at the opening sitting: the file is final and read; the sovereign enters `decision budget "C2c-1: window file sha256:<hash>; …"` (the hash is his act); counsel enters the promotion forecast naming the same hash; the opening push carries the file. `status.py`, **before it reads any criterion**, hashes the file at the assessed prefix and compares it with the hash in the latest `decision budget` on the prefix whose subject begins `C2c-1:` and with the promotion forecast's `args.window_sha256`; a mismatch refuses the whole assessment (`promote C2c-1: refused: window file changed`). That check lives in code (R9), not in the file, so an in-window edit of the file cannot remove it; and `frozen` names the file, so an in-window edit is also criterion 3's failure. No cycle: the file cites no seq; the budget rule finds the entry.

### R1 Numerals are housed

In `tools/status.py`, `tools/clerk.py` and `tools/value.py`: no integer, fraction or float literal outside `{0, 1, −1}`; no string literal that parses as a number or as an instant in §4's `ts` form; except (a) a string that is exactly a key of the window file's `numbers`, and (b) the constants the file's `spec_constants` lists with the section that fixes them (per-mille 1,000 and 999, Laplace's 1 and 2, the clock's 8 and 60, the printed precision 6), each of which appears in code as a named lookup into that table. Every number a criterion needs is a `numbers` key named by one of its `args`; the kinds declare which `args` are numeric (`counted`, `kernel`, `threshold`, `grace`, `min_rows`, `max`) and every other `args` value is an enumeration of the kind. Dates and seqs of windows are found by `opens` and `end`, never written.

**Pin `numerals_housed`.** Twins: (1) the three files as proposed pass the scan (numeric and instant literals, and numeric or instant strings, outside the two exceptions); (2) every numeric `args` of every criterion of every window file on `main` resolves to a `numbers` key holding a number (a `null` is a finding). Mutants: `P0 = Fraction(6, 11)` restored (twin 1); `6900` (twin 1); `int("6900")` (twin 1); `"2026-11-17T12:00:00Z"` (twin 1); `20.0` (twin 1); `math.log(999)` written inline instead of through the table (twin 1); a criterion whose numeric `args` names a missing key (twin 2).

### R2 Criteria are a closed set of kinds, each three-valued

A criterion is `{id, kind, args, evidence?, text}`; `kind` is one of `verified_run`, `tree_bounds`, `pins_killed`, `eprocess`, `no_claim_past_due_unescalated`, `ratchet`, `count_zero`, `undertakings_kept`, `no_veto`, `ratio` (ten). A kind outside the set refuses the whole assessment. Each prints one of three values in this order (M.2): `unmet` when the inputs supplied already show failure; `unknown (no <evidence>)` when the `evidence` it names is absent; else `met` or `unmet`. The line printed is `criterion <id>: <text> <value>`.

**Pin `criteria_three_valued`** (on `count_zero`, which reads the acts evidence and the log, and on `pins_killed`, which reads the run and the tree). Twins: (1) acts supplied, zero repairs → `met`; (2) no acts, nothing else failing → `unknown (no acts)`; (3) acts supplied, one repair → `unmet`; (4) M.2's distinguishing twin on `pins_killed`: no run file, and `pins/pins.py` at the tree lacks a pin the file names → `unmet`, not `unknown (no run)`. Mutants: absent evidence printed `unmet` (twin 2); absent evidence printed `met` (twin 2); `unknown` when a supplied input shows failure (twin 3); `unknown` wherever any input is absent even when a supplied one shows failure (twin 4).

**Pin `window_from_file`.** Twins: (1) `status.py --subject C2c-1` on a tree whose file lists criteria 1–12 prints exactly twelve `criterion` lines in the file's order carrying the file's `text`; (2) criterion 8 removed from the file → eleven; (3) criterion 9's `text` changed → that sentence printed; (4) a file naming kind `x` → the refusal line; (5) `--subject C2a` on a tree with `transcripts/windows/C2a.json` prints C2a's criteria as that file lists them. Mutants: a criterion added in code (twin 2); the file's `text` ignored (twin 3); a kind outside the set accepted (twin 4); C2a assessed from code rather than its file (twin 5, the present `assess`).

### R7 The enforcement map is a ledger; hand rows have deadlines; the ratchet

Each row of `tools/enforcement.json` is `{enforcer: code:<path:fn> | hand:<who>, witness: <pin id or ''>, deadline: <instant or ''>}`; the map's own check refuses a `hand` row without a deadline; the clerk prints a `W4 hand-row <row>` line for a `hand` row past its deadline, `ESCALATED`, held by counsel. Criterion 8 reads the rows the file names (`runner`): `met` when the row read `hand` at the opening push's parent and `code` at the assessed prefix, its `witness` names a pin KILLED in the verified run, and the runner evidence shows every workflow of `renavondata/opencode-runner` at its `main` fetching at least one definition whose path exists in jack's tree at the assessed prefix at the recorded sha; `unknown (no runner)` without the evidence; `unmet` otherwise.

**Where the definitions live, and what a workflow is.** A GitHub Actions workflow must sit in `.github/workflows/` of the repository it runs in; it cannot be fetched and run from elsewhere. So the runner's workflows stay in `opencode-runner`, reduced to what only a workflow can hold — trigger, lane, permissions, concurrency, timeout — and each runs one script it fetches from jack's `main` at dispatch: `tools/runner/<job>.py` (the diary, the herald's merge loop, the session runner's steps, the courier, the monitor's verifier), built by a builder to `transcripts/runner/<job>.md` (counsel's text: what the job holds, when it runs, what it does in order, what it never does). The thin workflows are installed once by the sovereign (a repair, listed); after that a change to what a job does is a proposal in jack. Counsel writes the texts and never the scripts (SPEC §10.8).

**Pin `ratchet_row_moves`.** Twins: (1) `runner: hand` at the opening tree and `code:tools/runner` with a KILLED witness at the prefix, evidence showing each workflow fetching a path that exists at the recorded sha → `met`; (2) row not moved → `unmet`; (3) moved, witness not KILLED → `unmet`; (4) moved and KILLED, no evidence → `unknown (no runner)`; (5) evidence showing one workflow fetching nothing → `unmet`; (6) evidence recording a path absent from the tree, or present at another sha → `unmet`; (7) the row `code` at both trees → `unmet`; (8) another row moved, `runner` not → `unmet`; (9) a `hand` row with no deadline → the map's check refuses. Mutants: the opening tree not read (7); the witness not read (3); the evidence not read (5) or its shas not compared (6); any row accepted (8); the deadline check dropped (9).
