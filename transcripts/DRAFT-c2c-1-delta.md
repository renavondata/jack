## Amendment 1 (17 November, counsel-5; criterion 10 asks for one undertaking kept inside the window — before the opening, one clause)

**Why.** The audit (`transcripts/AUDIT-criteria-20261117.md`, C2c-1 row 10) classes criterion 10 as empty "as an in-window delivery test when no undertaking falls due before exit": counsel can match every open row with a forecast due after the exit, keep none, and the criterion reads `met`. §5 of this brief already said so under "Counsel's interest". It is to counsel's cost to close it.

**The clause.** Criterion 10 is also `unmet` unless at least `undertakings_due_min` undertakings of counsel's with `args.window` `C2c-1` have a `resolves_by` inside the window, at or before the assessed instant, and are resolved 1 at or before it. The window file's `numbers` gains `undertakings_due_min: 1`, and criterion 10's `args` gains `"due_min": "undertakings_due_min"`. Nothing else of R5 or of the criterion changes.

**What follows from it.** The window cannot be promoted before one undertaking of counsel's has fallen due and been kept; counsel therefore enters, before the opening push, at least one whose due falls inside the seven days. This brief still states no minimum length: the first lawful prefix is the first at which that undertaking is resolved and every other criterion holds.

**Pin `undertakings_are_forecasts`, added twins.** (14) every undertaking of the window due after the assessed instant, none resolved → `unmet` (before this amendment, twin 4's case alone read `met`); (15) one of the window's undertakings due inside the window and resolved 1 on time, the others not yet due → `met`; (16) the only undertaking resolved 1 on time carries `args.window` `C2b` → `unmet`. Twin 4 stands as it is where another undertaking of the window has been kept. Mutants: the minimum dropped (14); another window's undertaking counted toward it (16).

## Amendment 2 (17 November, counsel-5; criterion 12 counts as object only what was declared and resolved — before the opening, one clause)

**Why.** The audit (the same file, C2c-1 row 12) classes criterion 12 as empty "as a check that substantive object work outweighs procedure": forecasts of any `world.` label, unanswered and with deadlines past the window, count as object, and an undeclared type prints a diagnostic and still counts.

**The clause.** For criterion 12 in this window, an entry is object only when it is (i) a `forecast` of a type that `transcripts/world-types.json` declares, entered inside the window, whose `resolution` is on the log at the assessed prefix, or (ii) that `resolution`. A forecast of a declared type that is unresolved at the assessed prefix is counted on neither side. A `forecast` inside the window of a type beginning `world.` that the file does not declare makes the criterion `unmet`, where R8 had it only printed. A3.4's bound and its count of procedure are unchanged, so this can only lower the object count: it tightens (A2.4). R8's second printed line, the ratio excluding scheduled types, is unchanged and still not tested.

**What it does not do.** It does not say that a scheduled stream is not object: that is reserved to the sovereign for C2c-3 (`reserved_to_the_sovereign`, row 37). It does not make the ratio a test of whether object work is worth doing. A declared type's forecasts, resolved in time by another party, still count however easy they were.

**Pin `object_declared`, added twins.** (7) ten forecasts of `world.renavon` inside the window with no resolution at the assessed prefix → counted on neither side, and the ratio read without them; (8) the same ten resolved by another party → counted as object, twenty entries; (9) one forecast of `world.padding` inside the window, undeclared → `unmet`; (10) the same forecast entered before the opening → no effect on this window. Mutants: unresolved forecasts counted as object (7); an undeclared type counted or merely printed (9); the window bound dropped (10).

## Amendment 3 (17 November, counsel-5; the main verbs follow a moved `main` — before the opening, one clause, a deliverable)

**Why.** `tools/jack` refuses a main verb when `HEAD` is not `origin/main` and treats a rejected push as "a refusal, never a retry". The herald merges every few minutes, so the sovereign's pastes have had to wait for a quiet minute: forty-two minutes at C2a-prime's opening (COUNSEL-OPEN row 68). Agreed with him that day: "the verbs merge a moved `main` and retry, every check repeated", as a deliverable of this window with a pin.

**The clause.** It is the builder's, in `tools/jack`, to `RUNBOOK.md`'s text for it, which counsel proposes first.

1. *At the start.* A main verb whose local `main` is behind `origin/main` fast-forwards to it and goes on. A local `main` that has commits `origin/main` lacks is refused, as now.
2. *At the end.* When the verb's push of `main` is rejected because `main` moved, the verb undoes its effects as it does today on any failure, fetches, fast-forwards, and **runs itself again from its first precondition**. Nothing is carried over: the entry is signed again on the new head of the log, with a new `parent`, `seq` and `ts`; `promote` runs the status tool again on the new `HEAD`; `amend` appends to the charter again; every refusal the verb has is tested again.
3. *`push BRANCH`.* The verb still never commits to BRANCH. When BRANCH does not contain `origin/main`, the verb builds, in a temporary worktree, one merge commit of BRANCH's head and `origin/main` whose tree is chosen path by path: where BRANCH's bytes equal those of their merge base, `main`'s; where `main`'s equal the merge base's or BRANCH's, BRANCH's; a path both changed differently refuses the push, and so does more than one merge base. The check of the tree, the run of record when one is required, and the read gate are all run on that merge commit, and it is what `main` is fast-forwarded to. On a rejected push this is done again from the start, on the new `origin/main`.
4. *The bound.* A verb runs itself at most `verb_retries` times (the window file's `numbers`, 5; for `push`, 3) and then refuses, naming the number: `main kept moving`.

**What it does not change.** No check is skipped or remembered from an earlier try. An entry is lawful only on the prefix it is finally entered on. The verb merges no proposal and closes none. A paste needs no guard that waits for a quiet minute, and a guard that is still in a paste is harmless.

**Pin `verb_follows_main`.** Twins, on fixtures with a remote that moves: (1) `main` gains one commit after `decision grant` has signed and before its push → the entry lands on the new head, its `parent` the new head's hash, and the first signature is on no branch; (2) the same with `promote`, where the commit that arrived makes the status tool print a criterion `unmet` → refused on the second try, nothing pushed; (3) `main` gains a commit before each of six tries → refused after five, naming the bound; (4) local `main` ahead of `origin/main` → refused at the start; (5) `push BRANCH` where `main` moved in `log.jsonl` and `transcripts/` only → one merge commit, the check run on it, `main` fast-forwarded to it, BRANCH's ref unmoved; (6) `push BRANCH` where `main` and BRANCH changed one file differently → refused, nothing built on `main`; (7) a rejected push during `push BRANCH` → the merge commit built again on the new `origin/main` and the check run again. Mutants: the first signature reused (1); the status tool not run again (2); no bound (3); a diverged local `main` rebased (4); BRANCH's ref moved (5); a textual merge accepted (6); the first try's check result reused (7).
