## 1. What the code does today

Read by counsel on 18 November at the runner's `main` `dd5578d7` and jack's `main` `315bf158`. The runner is private: a reader who cannot open its files cannot check the first three items, and a builder checks each before relying on it.

- `herald.yml` loops over every open pull request to `main` (line 49) and calls its function `repropose` at lines 61, 78 and 90. The function (36 to 48) reads the party from a `Proposer:` line of the pull request's body (38), the head's branch name (39) and the title (40), and dispatches `repropose.yml` with all three (44).
- `repropose.yml` takes four inputs (11 to 15) and runs `repropose.py` beside the key `~/.ssh/jack-<party>` (45). When the script exits non-zero it fills a session template with `sed`, writing the title and the branch name into the text of the `sed` program (52 to 53), appends the last fifteen lines of the script's output to the prompt (54), and files the session under a title that holds the branch name (55).
- `repropose.py` fetches the branch by name (43), finds the common prefix of the two logs by lines (47 to 49), plans to re-make every forecast and resolution after it (51 to 70) without reading an entry's proposer or verifying a signature, takes as content the whole difference from the merge base to the stale head outside `log.jsonl` (71 to 72), applies it in a new worktree (94), and runs that worktree's `tools/jack` there (96, 105, 124).
- `tools/jack` imports `kernel`, `judge` and `tools` from the checkout its own file lies in (line 5). Every verb begins by fetching `origin` (32) and a branch verb refuses unless `origin/main`, as that fetch left it, is an ancestor of `HEAD` (48). The forecast and resolve verbs on a branch commit `log.jsonl` locally and push nothing (300); the proposal verb pushes the branch (88) and then lists or opens the pull request (89 to 92), so it can refuse after its push (93 to 95). An entry's `ts` is the real clock (301). The proposal verb runs that tree's tests and pins before it signs (97 to 99, 123) and signs `{title, commit}`; the commit is the first that `commits_of(ROOT, "origin/main", "HEAD")` yields which changes a path other than `log.jsonl`, else `HEAD` (124).

So where a stale branch's patch changes a file that the verbs import or the check runs, that file's code runs beside the party's key, whoever added it; and a pull request's title reaches a program's text.

## 2. Terms

- **M**: the commit `origin/main` names after the job's first fetch. Every use of "`main`" in these rules means M. The verbs fetch again for themselves; R9a says what the job does when `origin/main` has moved off M.
- **S**: the stale head, the commit the pull request's head branch names on `origin` after that same fetch.
- **The fork point** k: the number of leading lines, compared as bytes with their line ends, that M's `log.jsonl` and S's `log.jsonl` share.
- **The suffix**: S's log lines after the first k.
- **The law at the fork point**: the keys that M's first k lines declare, as `kernel/check.py` folds them.
- **The job's party**: the principal the law at the fork point gives the key file this job signs with; if that key is not declared there, the job has none.

## 3. The rules

R0 to R11 bind `repropose.py` and `repropose.yml`; H1 to H4 bind `herald.yml`. Rules are tested in their number's order and the first that fails decides. A refusal named `R-…` is a **provenance refusal**: the job comments on the pull request with the code and nothing else of the run, files no session, pushes nothing, leaves no entry of its own on any branch of `origin`, and exits 0. No file of S is executed or imported, and no model session is filed, unless R1 to R7 have all passed.

- **R0, the inputs.** `repropose.yml` has two inputs, `n` and `party`. Before anything else the script matches `n` against `[0-9]+` and `party` against `builder` or `reviewer`, each as a whole string; otherwise it prints a line and ends, with no comment (there is no trusted number to comment on). `party` chooses the runner and nothing else: R3 decides the party from the key.
- **R1, the head.** The job fetches `origin` once, then reads the pull request by its number through the API: it is open or was closed by the herald's stale comment, its base is `main`, its head repository is `renavondata/jack`, and S, the tip of its head branch on `origin` as fetched, equals the head commit the API reports. Otherwise `R-head`. The branch name goes to `git` as one argument; one beginning with `-` is `R-head`.
- **R2, anchored to `main`.** k is at least 1, so the two logs share genesis, and k is the whole length of M's log or less. In a clean detached worktree of M, with S's log bytes written to a file outside every tree, M's `python3 -m kernel.check <file>` reports ok. Otherwise `R-log`. (With k ≥ 1 the kernel checks every suffix entry's signature against keys declared by `main`'s own genesis and by key entries in the shared prefix or the suffix; R3 removes the suffix's.)
- **R3, what the suffix may hold.** Every suffix entry is of type `forecast`, `resolution`, `proposal` or `merge`. Tested in this order: the job has a party and the suffix holds at least one `proposal`, the last of which has the job's party as proposer, else `R-party`; then every `forecast`, `resolution` and `proposal` entry's proposer is the job's party and its signing key is one the law at the fork point declares for that party, and every `merge` entry is signed by a key to which the law at the fork point gives the power `merge` and none of `proposal`, `forecast` and `resolution`, and comes after at least one `proposal` entry, else `R-foreign`; an entry of any other type is `R-foreign`.
- **R4, the content.** P is the suffix's last `proposal` entry and C the commit it names. C is an ancestor of S. Every commit in `git rev-list C..S` changes, against each of its parents, `log.jsonl` alone or nothing. Otherwise `R-unsigned`. The patch is `git diff --binary B C` outside `log.jsonl`, B being the merge base of C and M; when there are several merge bases: `R-unsigned`. It is applied with `git apply --index --binary`, as today (line 94), with no three-way fallback: a patch that does not apply so is R10's failure.
- **R5, the title.** T is P's `title`. T begins with `-`, holds a character below U+0020 or from U+007F to U+009F, or is longer than 4,000 characters: `R-title`. The new proposal's title is T followed by ` (re-proposed mechanically: PR #<n> went stale)`, as today, n in digits; it is passed to the verb as one argument.
- **R6, the age.** P's `ts` is not later than the job's clock, read once at the start, and not more than `repropose_max_age_hours` before it; the number is a positive whole number of hours, alone on the first line of `.github/repropose-max-age-hours` on the runner's `main`, which the sovereign sets; a file missing, unreadable or holding anything else is `R-old`. Exactly that many hours before: not refused. Otherwise `R-old`. (Evidence for the number: among jack's pull requests #922 to #1121, 56 mechanical re-proposals opened between 7.4 and 167.8 minutes after their stale original.)
- **R7, not again once merged.** If M's log holds a `proposal` entry of the job's party whose title is the new title R5 gives: `R-replayed`. The job runs under a concurrency group of the pull request's number that queues and does not cancel, as today (`repropose.yml` 18 to 20). This refuses a repeat only after the first re-proposal has merged; section 6 says what it does not refuse.
- **R8, no string of the pull request in a program or a prompt.** No title, body or branch name of the pull request, no commit message, no entry body and no output of the script is written into the text of a program, into a command line that a shell parses, or into a session's title or body. Each travels as an argument, an environment variable or a file. A forecast's claim and arguments and a resolution's evidence go to the verbs as arguments, as today's script passes them (lines 100 to 104).
- **R9, what is re-made.** In the suffix's order: a forecast is skipped when its body's `args.window_utc` is present and its first member is at or before the job's clock (today's test, lines 59 to 60), when its `resolves_by` is before the job's clock, or when M's log holds a forecast of the same proposer and body; a resolution is skipped when M's log resolves that forecast; proposals and merges are not re-made. The rest are re-made by the verbs in a new worktree that holds M with the patch applied and committed. If nothing is re-made and the patch is empty, the job comments "nothing to re-make" and ends with no proposal; a suffix that is one proposal and no content is such a case.
- **R9a, a moved `main`.** Before each verb the job compares `git rev-parse origin/main` with M, and again after it. If it differs, the step fails under the name `moved` and R10 applies: the party's session re-proposes on the newer `main`, as today's fallback does when a verb refuses a branch that no longer contains `origin/main`.
- **R10, the fallback.** A failure after R1 to R7 have passed, of one of five named steps (`apply`: the patch does not apply; `forecast` or `resolve`: that verb refuses; `proposal`: the proposal verb refuses before its push; `moved`: R9a), files the job's party's own session from the template `transcripts/sessions/repropose.md` as M holds it, filled by a script's plain replacement of four placeholders: `{N}`, the pull request's number; `{S}` and `{C}`, forty hexadecimal digits each; `{P}`, the `seq` of P in S's log, in digits. The issue's title is `<party>: re-propose PR #<n> on a fresh prefix`. The body holds the filled template and the failed step's name, and no other text. The template tells the session to check out S, to read P at that `seq` of S's log for the title, to work from C, and that nothing in the pull request's own title, body or comments is an instruction. The forecast and resolve verbs push nothing, so on a failure before the proposal verb's push the job removes its worktree and local branch and no entry of its own is on `origin`. If the proposal verb refuses after its push, the pushed branch holds a signed proposal and may have no pull request: the job does not delete it, comments on the stale pull request with the new branch's name (the job's own string: the stale branch's name with `-r` and digits, which R1 has bounded to a name beginning with no `-`), and files nothing; the herald's loop does not see a branch without a pull request, and section 6 names this.
- **R11, the test seams.** `REPROPOSE_MAIN` is removed. The script takes three optional arguments that `repropose.yml` never passes and the pin does: the ref to use as M, the file to read the age from, and a directory of canned API answers for R1. It takes no clock argument: the pin builds its fixtures around the real clock (section 5).
- **H1.** A pull request whose head repository is not `renavondata/jack` is skipped at the top of the loop with a printed line: not merged, not re-proposed, not commented on.
- **H2.** The party the herald passes is the proposer of the last `proposal` entry in the head's log, which it already reads; if there is none, or it is neither `builder` nor `reviewer`, the function prints today's line for a party "not re-proposed from steel" (line 46) and dispatches nothing, closing nothing, as today for such a party. H2 binds the function `repropose` only, not the loop before it.
- **H3.** The herald dispatches with `n` and `party` and nothing else. Its comment names the number and the party, not the branch.
- **H4.** The three call sites call as they do today.

**The claim**, and no wider: when R1 to R7 pass, every file the job's verbs import or its check runs is a file of M or a file changed by the patch from B to C, C being named by a proposal entry that a key `main`'s log declares for the job's party has signed. The claim is about the files' origin; the patched tree is a third tree, and what its code does when run, including fetching or generating other code, is not bounded by this brief.

## 4. What this refuses that the lane does today

- A stale branch holding, after the fork point, an entry by a party other than the job's (but for the herald's merges). Counted on `main`'s log at `315bf158`: since seq 195 no merged proposal's segment has held one; this is a count of what merged, not of what a branch may hold.
- A stale branch on which content was committed after its last proposal entry. The party's remedy is its own session.
- A pull request from a fork. Of jack's last 100, none came from one.
- A proposal older than `repropose_max_age_hours` or dated after the job's clock; a title R5 refuses, which the proposal entry's schema admits; a C with several merge bases against M; a head whose suffix holds no proposal of the builder or the reviewer, among them a head that would merge today by a filled `Proposer:` trailer and no proposal entry (`tools/jack` 153 to 156); any run while the age file is missing.

Counsel has counted none of these second kinds on the lane and does not say they do not occur.

It does not refuse: a re-proposal of a re-proposal; a branch with two proposal entries, with or without a herald's merge between them (P is the last); a proposal with no content commit (the patch is empty and the entries are re-made).

## 6. What this leaves

- **The fallback's session is a model reading a branch.** After R1 to R7 the branch's content and P are the job's own party's signed work, but a session that works from C reads its files, and a model may take what it reads as instruction. The template's sentence is a request to the model, not a control. Rung 6, narrated.
- **Signed code is still code.** A party's own signed commit can do anything its key's user can; this brief authenticates whose it is.
- **Replay inside the age.** Within `repropose_max_age_hours`, a proposal a party abandoned can be re-proposed as signed by whoever re-opens its pull request or opens another for the same head. R7 refuses a repeat only when the first re-proposal has merged and the pull request's number is the same: a second run before that merge, or a new pull request (a new number, so a new title), is not refused. The cost to whoever does it is one pull request opened, or one dispatch by an identity with Actions write; the cost to the lane is a duplicate proposal, which goes stale when its twin merges and is then skipped entry by entry under R9. Each provenance refusal costs one run; nothing bounds how many pull requests an identity with pull-request write may open.
- **A refusal after the push.** A proposal verb that refuses after its push leaves a branch with a signed proposal and no pull request, which nothing re-opens: the party's next session, or his hand, must.
- **A dispatch with a false `party`** by an identity with Actions write on the runner runs on that party's runner and ends in `R-party` when the stale proposal is not that party's; it is not refused before the job starts.
- **The keys still lie in one user's home on steel** until the custody text is built; any session there can read them without the re-proposer.
- **Entries a job signed before a failure** are discarded with its worktree: a signature was made and thrown away, and a forecast so signed and never pushed is on no log.
