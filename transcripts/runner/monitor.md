# The monitor — definition (counsel's text, draft v5, 8 November 2026, after the reads on runner issues #376 and #383–#406 and pre-reads; CHARTER A2.8)

A2.8 says three things: the head hash of the log is published on every push; a monitor that the owner does not operate verifies that each published hash extends the last and that both checkers accept the log; and it writs Guy on any failure. The first and third are code this text is written to; the second is partly a fact about who runs the code, and this text says which part is met, which is not, and how each is read from a record.

**The head hash** is SPEC §3's: the SHA-256 of the last line's bytes of `log.jsonl` (`kernel.log.line_hash`), the `parent` the next entry must name. `python3 -m kernel.check` prints `{"ok": true, "entries": N}` and not the hash (SPEC §9); the scripts below compute it from the file, and the kernel's `entries` ties it to a seq.

## Publication (jack's own workflow; a trusted-base change, so by `push`)

`.github/workflows/publish.yml`, its own workflow, **on push to `main` only** — never on `pull_request`, so no proposal's run holds a writing token — with `permissions: contents: write` (this repository only), **no concurrency group** (a group cancels a queued run when a third arrives, and a cancelled run is a push with no line), and its steps written out in the workflow itself, which is trusted base, so that nothing outside the trusted base decides what is published:

1. Check out the pushed commit; run both checkers over its `log.jsonl`; stop red, publishing nothing, unless both print `ok` with the same `entries`. A published line is a verified head.
2. Compute `<seq>` (`entries − 1`) and `<hash>` (the last line's SHA-256), with `python3 -c` over the file.
3. Fetch the branch `hashes`; append one line `<seq> <hash> <commit> <instant>` to its file `HASHES`; commit and push; on a rejected (not fast-forward) push, fetch, re-append on the new tip and push again, up to five times. Concurrent runs each append their own line; the order of lines is the order their pushes land, not the order of `main`'s commits, and two lines may carry the same `seq` when a push to `main` added no entry. The verifier (below) therefore checks lines by commit, not by order.

The ruleset on `hashes` refuses force-pushes and deletion as `main`'s does, and requires no check (none exists for it). Who can write to it: this workflow's token; the jack-court App, which holds write on the repository (the herald's identity) and is not told to; and the owner (`enforce_admins` off, REPORT.md §8.1). A proposal cannot change what is published: the workflow is trusted base (SPEC §10.1) and the judge refuses a proposal that touches it, so the publisher changes only by the owner's push. Residue: a wrong line by the App or the owner is not prevented by the ruleset; it is detected by the verifier, which recomputes every line from the tree — the same residue as `main`'s, and A2.8 adds the verifier for it.

## Verification (the verifier; a public script, run by whoever runs it)

`tools/runner/workflows/verify.yml` (a builder's, written to this text) — a workflow whose steps hold the whole verifier inline, fetching nothing from jack's `main` at run time (a verifier that fetched its own code from the branch it verifies could be rewritten with it) — installed in a repository other than `renavondata/jack`, on GitHub-hosted runners (`runs-on: ubuntu-latest`), on a schedule, keeping its own record in that repository; the court holds its bytes in the tree and the runner evidence compares them:

1. Fetch `hashes` first, then clone `renavondata/jack` at `main` (in that order, so that every line's commit is at most as new as the `main` read; a line whose commit `main` does not yet hold is re-checked after one re-fetch of `main`, then refused).
2. Run both checkers over `main`'s `log.jsonl`; refuse unless both print `ok` with the same `entries`; compute the head's `<seq>` and `<hash>` as publication does.
3. Read `HASHES`, line by line, by commit: every line's `commit` is on `main`'s first-parent history; `log.jsonl` at that commit has `seq + 1` entries and its last line's SHA-256 is the line's `hash` — recomputed from the tree, never trusted from the file. Then **each head extends the last** (A2.8's words): order the lines by their commits' positions in `main`'s first-parent history and refuse unless, for each consecutive pair, the earlier commit's `log.jsonl` is a byte prefix of the later's (a published log replaced by another of the same length is caught here, not by step 4, which sees only the verifier's own runs). The file's own order and monotone `seq` are not required (publication, step 3); nor a line per first-parent commit — a `jack push` fast-forwards several commits and pushes once, and publication runs per push event, so completeness is step 5's and the evidence's: the head always published within the lag, and no `publish.yml` run concluding other than `success`.
4. Read the verifier's own record (step 7's file): from its **last `ok` line** — never a failure line, so a rewrite that failed once cannot become the checkpoint by being recorded — the `HASHES` line count n and the SHA-256 of `HASHES`'s bytes then, and that run's verified head `(seq, hash)`. Refuse unless today's `HASHES`'s first n lines hash to that digest (append-only) and today's `log.jsonl` has, at that `seq`, a line whose SHA-256 is that `hash` (the log extends what was verified; a rewrite of `main` and `hashes` together is caught here, which is what A2.8's "each head extends the last" asks). The first run compares nothing and records.
5. Lag: `main`'s head commit has a line, or its committer date is less than `lag` (one hour) before now (a publication in flight); a head older than that with no line is a failure.
6. On any failure, the writ first: one issue on the repository the verifier runs in, titled `monitor: <failure>` with the verdict, filed by the workflow's own token (`issues: write` on its own repository; GitHub-hosted runs act as `github-actions[bot]`, which needs no grant because the runner repository is not under the court's law and the bot is nobody's hand); its number goes into step 7's line, and if the filing itself fails the line ends `#none` — a failure line without its writ, which B7 counts against the monitor. The clerk prints a `W4 monitor` line for an open issue so titled; the evidence session copies every such issue with the record.
7. Append one line to the verifier's record, a file in its own repository: `<instant> <main commit> <head seq> <head hash> <HASHES lines> <sha256 of HASHES's bytes> <host> ok | <failure> #<issue>` — the count and the digest are what step 4 reads next time — where `<host>` is read from the Actions API's job object for the run itself: `github-hosted` when the job's `runner_group_name` is `GitHub Actions` and its `labels` are GitHub's (`ubuntu-latest`), else the `runner_name` (a steel job reads `steel-opencode-2`, group `Default`). The record is append-only by the same ruleset rule as `hashes`.

The verifier compares bytes it recomputes with bytes it recorded; it trusts no verdict of any earlier run of itself and nothing the publisher wrote except as a claim to check.

## Who runs it, and what "does not operate" means here

The script and its shell are public and anyone can install them in a repository of their own with an account of their own. The first instance runs from `renavondata/opencode-runner` on GitHub-hosted runners, as the workflow's own token: the **host** is GitHub's, not the owner's — no machine of his runs it, and the shell's bytes are the court's (compared as C2c-1's criterion 8 compares the courier's) — but the **configuration** is his: he can disable the workflow or change its shell. A changed shell is visible (the runner evidence); a disabled verifier is visible only as a record that stops, and nothing in the court notices a record that stops except a reader. So A2.8's operator clause is read as two tests, and B7 (`transcripts/RESEARCH-meta-jack-20261107.md`, on `main` once proposed) takes them as stated: (i) the newest line of the verifier's record is `github-hosted`, within twenty-four hours of the assessed instant, and `ok` — decidable from the monitor evidence; (ii) the account that owns the verifier's repository is one the owner does not control — the evidence decides a proxy, that the repository's owner login is neither `gfrmin` nor `renavondata` (B7 reports it, and tests it only if the sovereign rules that the bootstrap claim waits for a second instance), and no record decides control, so C2c-2's push adds a `hand` row to the enforcement map (`A2.8-operator`, with the deadline the sovereign sets, C2c-1 R7's shape) for the part the proxy cannot reach, unmet until a second instance in another login's repository exists and its record is copied in. The book's ch 12 §12.4 states the same residue and keeps stating it.

## Evidence the window file names

`transcripts/evidence/monitor-<stamp>.json`: the verifier's record copied into the court by the evidence session (read-only `gh api` on the verifier's repository: the record's lines, the repository's owner login, and for the newest run the job object's `runner_group_name`, `runner_name` and `labels`), every `publish.yml` run of `renavondata/jack` since the window's opening with its `head_sha` and `conclusion`, the workflow's `state` at the time of the copy, and every `monitor:` issue of the verifier's repository since the opening, open or closed, with its number and instants; B7's test reads it (a failure line since the opening names its issue's number and the issue is in the copy, or the writ was not filed).
