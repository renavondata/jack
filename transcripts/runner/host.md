# The host — the runner user on steel (counsel's text, draft v3, 8 November 2026; `opencode-runner` #188; `transcripts/runner/counsel-courier.md` §Who is counsel)

**What this text closes, and what it leaves open.** Every runner on steel runs as the login user `g`, whose home holds every party key and a `gfrmin` `gh` login with `admin:org`, `repo` and `workflow` scopes (#188), and `run.yml` exports whatever `key:` an issue body names. This text is the rule for #188's own fix — one runner user holding what the jobs read and none of `g`'s — and for the workflow changes that follow from it; a builder codes the installer and the changes to it, and the sovereign makes the host act once. It does not separate the parties' keys from one another: every job can still read every party key by path, so any session on steel can sign as any party, and the courier's refusal in §3 is a courtesy to the record, not a bound; the separation is C2c-2's, with a text of its own. It does not close the pushed-workflow route (§4). It binds nothing until the acts are made, and the sovereign reads it before the build (A2.10).

## 1. The user and its home

One system user, `jack-runner`: no password, login shell `/usr/sbin/nologin`, no sudo, home `/home/jack-runner` mode 700. Every runner registered for `renavondata/opencode-runner` on steel runs as it. Its home holds exactly:

- `~/git/jack`, a fresh clone of `renavondata/jack` over SSH with a deploy key, `~/.ssh/deploy-jack` (write: the verbs push branches — a proposal's, a merge entry's — and a push is not an act; no job step directs a verb that pushes `main` — those, `key`, `push`, `decision`, `amend`, are the sovereign's, and the runner holds no key of his — and a session that ran one would be refused twice over, by the log's powers for the key it holds and by `main`'s protection, which requires the `judge` and `tests` checks of every pusher that is not an administrator; the deploy key is none), through `~/.ssh/config` (`Host github-jack`, `IdentityFile ~/.ssh/deploy-jack`) and `~/.ssh/known_hosts` holding github.com's keys; `~/git/worktrees/jack/`, empty at the install;
- `~/.gitconfig`: `user.name jack-runner`, `user.email jack-runner@steel` — the entry commits and worktree commits are the runner's, no longer under the owner's name (the ledger's row 4);
- `~/.ssh/jack-builder`, `~/.ssh/jack-reviewer`, `~/.ssh/jack-herald`, `~/.ssh/jack-counsel-3` — the party keys the jobs sign with, as today;
- `~/.config/jack/app-id`, `~/.config/jack/app.pem` (the jack-court App, every job's `gh` identity through `gh-as-app`) and `~/.config/jack/gh-counsel` (counsel's token: `counsel-act.py` and `counsel-sign.py` read `COUNSEL_GH_TOKEN` from the environment, else this file);
- the runner installs, `~/.local/share/actions-runner-*`, moved whole from `g`'s home with their `.runner`, `.credentials`, `.credentials_rsaparams`, `_work`, `_diag` and `.env` (the model API keys, which `run.yml` says come from the runner's own `.env`);
- `opencode` on its `PATH` and its configuration (`~/.config/opencode`, `~/.local/share/opencode`: the provider and model definitions, copied from `g`'s; any provider login in them is removed — keys come from `.env`).

It holds no `gh` login (`gh auth status` under it reports none; every `gh` call in a job acts as the App or, in the courier, as counsel's token), nothing of `g`'s `~/.config/gh`, no `id_*` key of `g`'s, and no credential for any repository but jack's deploy key. `g`'s home is mode 700 and unreadable to it. The install requires no run in flight and no unpushed local branch in `~g/git/jack`: with the runners stopped the installer lists any local branch ahead of `origin` and stops if there is one (a stopped run's entries, `counsel-sign.py` step 1, are pushed first by the sovereign's hand).

## 2. The installer and its check (the builder's, under `tools/runner/host/`)

`tools/runner/host/install.sh`, run once by the sovereign as root on steel, idempotent, with a `--root DIR` mode that builds the homes and units under `DIR` for the pin. Inputs: a staging directory he fills by hand, `/root/jack-host/`, holding the four party keys, the three `~/.config/jack` files and the deploy key pair; a file in it that §1 does not name is refused by name, and a party key missing from it stops the install before any service moves. Steps, in order: create the user and home; stop and uninstall each runner service as root (`./svc.sh stop`, `./svc.sh uninstall` — the unit holds absolute paths and is re-made after the move); check `~g/git/jack` for local branches ahead of `origin` and stop if any; move each `~g/.local/share/actions-runner-*` directory whole into the new home and `chown -R jack-runner:jack-runner`; install and start each service as the new user (`./svc.sh install jack-runner`, `./svc.sh start` — the registration travels with `.runner` and `.credentials`; the first run proves it); place the staged files, mode 600, write `~/.gitconfig`, `~/.ssh/config` and `known_hosts`; clone jack over the deploy key; copy opencode's configuration from `g`'s home; `chmod 700 /home/g`; remove nothing else of `g`'s. It never reads `~g/.config/gh` and never copies a key it was not staged.

`tools/runner/host/check.sh`, run as root: per runner unit, its `User=`; the names of the files under `/home/jack-runner/.ssh` and `.config/jack`; `gh auth status` as `jack-runner` (expected: no login); whether `/home/g/.config/gh/hosts.yml` is readable to `jack-runner` (expected: no); as `jack-runner`, `git -C ~/git/jack fetch` and `git -C ~/git/jack push --dry-run origin HEAD:refs/heads/host-check` (expected: both ok). The sovereign adds, from his own login, `gh api repos/renavondata/opencode-runner/actions/runners` (expected: every runner `online`). Together they are the witness; he pastes them into a COUNSEL-OPEN row after the install.

Pin `runner_user_holds_no_login` (the reviewer's, on the installer in `--root` mode): twin — the staged files of §1 are placed and the home holds exactly §1's list; mutants — a `hosts.yml` or an `id_ed25519` in the staging directory is refused, not copied; a party key missing from the staging directory stops the install before any service moves; a local branch ahead of `origin` in the old checkout stops it.

## 4. The pushed workflow, left open

A push-triggered workflow runs the pushed copy of its own file, so whoever can push a `.yml` to a branch of the runner runs what they like on steel. Counsel's pushes reach GitHub as the sovereign's login: the drafting session pushes with his credentials (the courier text, §Custody; the runner's push events for `counsel-requests` show `gfrmin`). A ruleset restricting `.github/` with him as bypass actor therefore stops nothing, and without the bypass stops him too; the route stays open and is listed. After §1 what such a job reaches is what every job reaches — the party keys, counsel's token and the App — and no longer an `admin:org` login. Pushes made by the verbs from steel go over the deploy key, which GitHub attributes to the key's creator; the drafting session's stay `gfrmin`'s.
