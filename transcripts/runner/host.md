# The host — the runner user on steel (counsel's text, draft v10, 8 November 2026; `opencode-runner` #188; `transcripts/runner/counsel-courier.md` §Who is counsel)

**What this text closes, and what it leaves open.** Every runner on steel runs as the login user `g`, whose home holds every party key and a `gfrmin` `gh` login with `admin:org`, `repo` and `workflow` scopes (#188), and `run.yml` exports whatever `key:` an issue body names. This text is the rule for #188's own fix — one runner user holding what the jobs read and none of `g`'s — and for the workflow changes that follow from it; a builder codes the installer and the changes to it, and the sovereign makes the host act once. It does not separate the parties' keys from one another: every job can still read every party key by path, so any session on steel can sign as any party, and the courier's refusal in §3 is a courtesy to the record, not a bound; the separation is C2c-2's, with a text of its own. It does not close the pushed-workflow route (§4). It binds nothing until the acts are made, and the sovereign reads it before the build (A2.10).

## 1. The user and its home

One system user, `jack-runner`: no password, login shell `/usr/sbin/nologin`, no sudo, home `/home/jack-runner` mode 700. Every runner registered for `renavondata/opencode-runner` on steel runs as it. Its home holds exactly:

- `~/git/jack`, a fresh clone of `renavondata/jack` over SSH with the deploy key (write: the verbs push branches — a proposal's, a merge entry's — and a push is not an act; no job step directs a verb that pushes `main` — those, `key`, `push`, `decision`, `amend`, are the sovereign's, and the runner holds no key of his — and a session that ran one would be refused twice over, by the log's powers for the key it holds and by `main`'s branch protection — `repos/renavondata/jack/branches/main/protection`: required status checks `judge` and `tests`, administrators exempt (the repository's rulesets add only no-deletion and no-force-push) — which a deploy key, no administrator, cannot pass), through `~/.ssh/config` (`Host github-jack`, `HostName github.com`, `IdentityFile ~/.ssh/deploy-jack`) and `~/.ssh/known_hosts`, written by the installer from `https://api.github.com/meta`'s `ssh_keys` (one line `github.com <key>` each; the endpoint needs no login); `~/git/worktrees/jack/`, empty at the install;
- `~/.gitconfig`: `user.name jack-runner`, `user.email jack-runner@steel` — the entry commits and worktree commits are the runner's, no longer under the owner's name (the ledger's row 4);
- `~/.ssh/jack-builder`, `~/.ssh/jack-reviewer`, `~/.ssh/jack-herald`, `~/.ssh/jack-counsel-3`, each with its `.pub` (the verbs and `counsel-sign.py` read `KEY.pub`) — the party keys the jobs sign with, as today; `~/.ssh/deploy-jack` (its `.pub` is not placed: it is what the sovereign adds to jack's deploy keys, from the staging directory);
- `~/.config/jack/app-id`, `~/.config/jack/app.pem` (the jack-court App: the `gh` identity of the sessions, the herald, the diary and the re-proposer, through `gh-as-app`; the courier's `gh` acts as counsel's token instead) and `~/.config/jack/gh-counsel` (counsel's token: `counsel-act.py` and `counsel-sign.py` read `COUNSEL_GH_TOKEN` from the environment, else this file);
- the runner installs, `~/.local/share/actions-runner-*`, moved whole from `g`'s home with their `.runner`, `.credentials`, `.credentials_rsaparams`, `_work`, `_diag` and `.env` (the model API keys, which `run.yml` says come from the runner's own `.env`);
- `~/.npm-global/`, copied whole from `~g/.npm-global/` (it holds the `opencode` binary, `/home/g/.npm-global/bin/opencode` today), with `/home/jack-runner/.npm-global/bin` written into each runner install's `.path` file (the file the runner prepends to every job's `PATH`); `~/.config/opencode/`, copied whole from `g`'s (the provider and model definitions); nothing of `~g/.local/share/opencode/` is copied — its `auth.json` is a provider login, the rest is cache — and the keys come from `.env`.

"Exactly" is of what the install places; the jobs then write their own runtime files there — `~/.config/jack/.token` (the App token `gh-as-app` caches for fifty minutes), the worktrees, the runners' `_work` and `_diag`, and the `safe.directory` lines `actions/checkout` adds to `~/.gitconfig` — and nothing else.

It holds no `gh` login (`gh auth status` under it reports none; every `gh` call in a job acts as the App or, in the courier, as counsel's token), nothing of `g`'s `~/.config/gh`, no `id_*` key of `g`'s, and no credential for GitHub but jack's deploy key, the App's files and counsel's token (which files and closes issues on the runner, the grant of seq 2131). `g`'s home is mode 700 and unreadable to it. The install requires no run in flight and no unpushed local branch in `~g/git/jack`: with the runners stopped the installer lists any local branch ahead of `origin` and stops if there is one (a stopped run's entries, `counsel-sign.py` step 1, are pushed first by the sovereign's hand).

## 2. The installer and its check (the builder's, under `tools/runner/host/`)

`tools/runner/host/install.sh`, run by the sovereign as root on steel; re-runnable: each step checks its end state first and skips when it already holds (the user exists; no `~g/.local/share/actions-runner-*` remains; each unit's `User=` is `jack-runner`; each staged file is in place with the staged bytes), so a second run after a complete first run changes nothing, and a run after an interrupted one finishes it. `--staging DIR` names the staging directory (default `/root/jack-host/`); `--root DIR` is the pin's mode: with `--old-home` pointing at a fixture, it runs the checks and the file placement under `DIR/home/jack-runner/` instead of `/home/jack-runner/`, creates no user, moves no runner, touches no unit, and prints the commands it would run for those. Inputs: the staging directory he fills by hand, laid out as the home it feeds — `DIR/.ssh/jack-builder`, `jack-builder.pub`, `jack-reviewer`, `jack-reviewer.pub`, `jack-herald`, `jack-herald.pub`, `jack-counsel-3`, `jack-counsel-3.pub`, `deploy-jack`, `deploy-jack.pub`; `DIR/.config/jack/app-id`, `app.pem`, `gh-counsel` — thirteen files, twelve of them copied to the same relative path under the home with mode 600 and `deploy-jack.pub` left where it is; any other file in the staging directory is refused by name and the install stops; any of the thirteen missing stops it too. `--old-home DIR` names the old home (default `/home/g`), from which the runner installs and `.npm-global/` and `.config/opencode/` are taken and whose `git/jack` is checked. Steps, in order — the checks first, before any service is touched: refuse if any job is running — a process whose executable is `Runner.Worker` under any of the old home's `.local/share/actions-runner-*/bin/` directories (`pgrep -f 'OLD/.local/share/actions-runner-[^/]*/bin/Runner.Worker'`), the three units #188 names and any registered since; refuse if `OLD/git/jack` has a local branch ahead of `origin` (a stopped run's entries, `counsel-sign.py` step 1, are pushed first by the sovereign's hand); check the staging directory. Then: create the user and home; stop and uninstall each runner service as root (`./svc.sh stop`, `./svc.sh uninstall` — the unit holds absolute paths and is re-made after the move); place the staged files and write `~/.gitconfig`, `~/.ssh/config` and `known_hosts`; clone jack over the deploy key and verify one fetch; copy `.npm-global/` and `.config/opencode/`; `chown -R jack-runner:jack-runner /home/jack-runner` (everything placed so far is the user's; the moved runner directories are chowned as they arrive); move each `OLD/.local/share/actions-runner-*` directory whole into the new home, write its `.path`, and `chown -R jack-runner:jack-runner`; only then install and start each service, as root, with `jack-runner` as the service account (`./svc.sh install jack-runner`, `./svc.sh start` — the registration travels with `.runner` and `.credentials`; the first run proves it), so no job starts before its key, identity, checkout and `.env` are in place; `chmod 700 OLD`; remove nothing else of the old home's. It never reads `OLD/.config/gh` and never copies a key it was not staged.

`tools/runner/host/check.sh`, run as root, each line `ok` or `FAIL` and exit 1 on any `FAIL`: per runner unit (the three #188 names and any later `actions.runner.renavondata-opencode-runner.*`), `User=jack-runner`; the files under `/home/jack-runner/.ssh` are exactly the nine placed names plus `config` and `known_hosts`, and under `.config/jack` exactly `app-id`, `app.pem`, `gh-counsel` and, once a job has run, `.token`; every file under both owned by `jack-runner`, mode 600 (`config` and `known_hosts` 644); `gh auth status` as `jack-runner` (expected: no login); whether `/home/g/.config/gh/hosts.yml` is readable to `jack-runner` (expected: no); as `jack-runner`, `git -C ~/git/jack fetch` and `git -C ~/git/jack push --dry-run origin HEAD:refs/heads/host-check` (expected: both ok). The sovereign adds, from his own login, `gh api repos/renavondata/opencode-runner/actions/runners` (expected: every runner `online`). Together they are the witness; he pastes them into a COUNSEL-OPEN row after the install.

Pin `runner_user_holds_no_login` (the reviewer's, on the installer in `--root` mode): twin — the twelve placed files, `.gitconfig`, `.ssh/config` and `known_hosts` are placed and nothing else is written under `DIR` (the runner installs, the clone and the copied directories are the live steps `--root` prints and does not make); mutants — a `hosts.yml` or an `id_ed25519` in the staging directory is refused, not copied; a party key missing from the staging directory stops the install before any service moves; a local branch ahead of `origin` in the old checkout stops it.

## 3. The workflow changes

- `run.yml`, `diary.yml`, `herald.yml` and `repropose.yml` fall back today to "identity: owner login" when the App's files are absent. After the install there is no owner login: in each, the `else` branch of that test prints `no identity: the App's files are absent` and exits 1, the job's failure being the record; in `run.yml` the test moves ahead of the `started:` comment, and on refusal the step posts `refused: no identity (the App's files are absent)` on the issue with the repository token before exiting.

## 4. The pushed workflow, left open

A push-triggered workflow runs the pushed copy of its own file, so whoever can push a `.yml` to a branch of the runner runs what they like on steel. Counsel's pushes reach GitHub as the sovereign's login: the drafting session pushes with his credentials (the courier text, §Custody; the runner's push events for `counsel-requests` show `gfrmin`). A ruleset restricting `.github/` with him as bypass actor therefore stops nothing, and without the bypass stops him too; the route stays open and is listed. After §1 what such a job reaches is what every job reaches — the party keys, counsel's token and the App — and no longer an `admin:org` login. Pushes made by the verbs from steel go over the deploy key, which GitHub attributes to the key's creator; the drafting session's stay `gfrmin`'s.
