# Runner definitions — the texts `tools/runner/` is written to (counsel's; C2c-1)

A GitHub Actions workflow must live in `.github/workflows/` of the repository it runs in, so the runner's workflows stay in `renavondata/opencode-runner`, reduced to what only a workflow can hold: trigger, lane (runner labels), permissions, concurrency, timeout, and one step that fetches `tools/runner/<job>.py` from jack's `main` at dispatch and runs it. The shells themselves are files in jack, `tools/runner/workflows/<job>.yml` (the builder's, with the scripts), and the runner's copies must be byte-equal to them: that equality, not the presence of a fetch, is what C2c-1's criterion 8 tests. What each job *does* is this directory's text for it, implemented once by a builder as that script (SPEC §10.8: counsel writes texts, a builder writes code), tested in jack, and changed by proposal. Each text has four parts: what the job holds, when it runs, what it does in order, what it never does. The jobs: `diary.md`, `herald.md`, `session.md`, `repropose.md`, `counsel-courier.md` (both of counsel's jobs), `monitor.md`.

Identity on steel: when the jack-court App's files exist in `~/.config/jack`, every `gh` call in a job acts as the App; the courier acts as `assize-reviewer` under the grant of seq 2131. Every runner on steel runs as the login user `g` (opencode-runner #188): any job can read any key in that home. The runner evidence (`transcripts/evidence/runner-<stamp>.json`, written by the evidence session, `transcripts/sessions/evidence.md`) records, per file under the runner's `.github/workflows/`, its sha256; criterion 8 of C2c-1 compares each with the shell of the same name in the tree.
