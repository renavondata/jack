# Runner definitions — the texts `tools/runner/` is written to (counsel's; C2c-1: the courier only)

A GitHub Actions workflow must live in `.github/workflows/` of the repository it runs in, so the runner's workflows stay in `renavondata/opencode-runner`, reduced to what only a workflow can hold: trigger, lane (runner labels), permissions, concurrency, timeout, and one step that fetches `tools/runner/<job>.py` from jack's `main` at dispatch and runs it. The shells themselves are files in jack, `tools/runner/workflows/<job>.yml` (the builder's, with the scripts), and the runner's copies must be byte-equal to them: that equality, not the presence of a fetch, is what C2c-1's criterion 8 tests. What each job *does* is this directory's text for it, implemented once by a builder as that script (SPEC §10.8: counsel writes texts, a builder writes code), tested in jack, and changed by proposal. Each text has four parts: what the job holds, when it runs, what it does in order, what it never does. In C2c-1 one job is written here and built: `counsel-courier.md` (both of counsel's jobs, the sign job and the acts job). `monitor.md` is C2c-2's. The diary, the herald, the session runner and the re-proposer stay in the runner as they are, `hand` rows of the enforcement map with deadlines; their texts come to this directory when a window needs them, not before.

Identity on steel: when the jack-court App's files exist in `~/.config/jack`, every `gh` call in a job acts as the App; the courier acts as `assize-reviewer` under the grant of seq 2131. Every runner on steel runs as `jack-runner`, whose home holds every party key and no login of the owner's (`transcripts/runner/host.md`; opencode-runner #188): any job can read any party key in that home. The runner evidence (`transcripts/evidence/runner-<stamp>.json`, written by the evidence session, `transcripts/sessions/evidence.md`) records, per file under the runner's `.github/workflows/`, its sha256; criterion 8 of C2c-1 compares each with the shell of the same name in the tree.
